# JDK 17 migration diagnostics for legacy Maven builds

Use this reference when an older Maven build fails after moving from Java 8 to
JDK 17, especially when it uses lifecycle-forking coverage plugins, bytecode
generation, legacy mocking, or old servlet containers. Treat each item as a
diagnostic hypothesis to prove from the current build, not as a version pin.

## Establish the effective build first

Capture the exact JDK and Maven versions, then compare the normal and failing
lifecycles:

```bash
java -version
mvn -version
mvn help:effective-pom -Doutput=target/effective-pom.xml
mvn dependency:tree -Dverbose
mvn clean verify
```

Read the failing execution ID and plugin version from the Maven log. A parent
`pluginManagement` entry does not prove that a lifecycle fork or module uses
that version; the effective POM and execution log are authoritative.

## Packaging and lifecycle forks

- If a lifecycle fork selects an obsolete default packaging plugin, declare a
  JDK-compatible version in the module's active `build/plugins` section. Choose
  the version from the plugin's compatibility documentation and repository
  policy rather than copying a fixed version from an incident.
- Do not hard-code `target/` or a literal artifact name in assembly and copy
  descriptors. Coverage or instrumentation plugins may redirect
  `project.build.directory`, `project.build.outputDirectory`, or
  `project.build.finalName`. Reference those Maven properties and use an
  explicit destination name only when the delivered artifact contract needs it.
- Confirm whether the plugin actually forks the lifecycle in this project
  before attributing changed paths or skipped executions to the fork.

## Generated code and bytecode tools

- When methods generated by Lombok or another annotation processor disappear,
  verify processor execution and use a release documented to support JDK 17.
- When a legacy mocking or bytecode library fails with reflective-access
  errors, prefer upgrading or removing it. If a temporary `--add-opens` bridge
  is unavoidable, add only the packages named by the failure, isolate the flags
  to the legacy test profile, apply them to each affected test runner, and never
  copy them into the production JVM configuration.
- Re-run from `clean`; stale instrumented classes can make a correct source fix
  appear ineffective.

## Runtime classpath conflicts

For `NoSuchMethodError` or `NoClassDefFoundError`, use the verbose dependency
tree to find which artifact wins. Pin or exclude only the conflicting module,
then prove the runtime or test classpath contains the intended class version.
Common collision families in older web applications include Hamcrest, servlet
APIs, embedded containers, and standalone test servers.

## Framework behavior changes

Mock request URLs and other normalized values can change across framework
upgrades. Compare the observed value with the target framework's release notes
before changing tests. Update an expectation only when the new value is the
documented contract, not merely because the assertion failed.

## Security findings during migration

Do not suppress a dependency finding because its product name looks wrong.
Re-run the dependency tree and source or reachability evidence for the exact
artifact and CVE. If the match is demonstrably false, scope the suppression to
the exact artifact/version and finding identifier, include a concrete
justification and expiry or review date where supported, then rerun the scan
without the suppression to preserve the original evidence.

## Completion gate

Run the repository's full, no-skip build on JDK 17, including unit, integration,
packaging, coverage, and dependency-security phases. Record any temporary
module-opening flags or compatibility pins as migration debt with an owner and
removal condition.
